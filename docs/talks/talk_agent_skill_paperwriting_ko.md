# 하네스 엔지니어링
## 모델에게 "말 거는" 것을 넘어, **구조에 넣어 일 시키기**

논문 한 편을 *혼자 쓰지 않고* 역할 가진 에이전트·스킬·메모리의 **오케스트라**로 작성·검증·학습시킨 실제 사례.

사례: 이 저장소의 체세포 변이 해석 프리프린트(EN/KO) 한 작업 사이클.

## 하네스 엔지니어링이란?

**하네스(harness) / 컨텍스트 엔지니어링** = 모델 *주변의 구조*를 설계하는 일.

- 루프 · 도구 · 서브에이전트 · 스킬 · 메모리 · 검증 게이트 · 오케스트레이션

| | 프롬프트 엔지니어링 | 하네스 엔지니어링 |
|---|---|---|
| 대상 | 프롬프트 하나를 튜닝 | 모델을 둘러싼 *시스템* 설계 |
| 질문 | **"무슨 말을 거는가"** | **"어떤 구조에 넣어 일 시키는가"** |
| 단위 | 한 번의 호출 | 여러 작업자·단계·게이트의 흐름 |

> 생태계에서 실제로 쓰는 말이다 — 패턴(Pipeline / Producer–Reviewer / Supervisor)에서 에이전트 팀을 자동 생성하는 "harness" 플러그인도 있다. 단, **우리 것은 손으로 짓고 손으로 튜닝**했다.

<!-- 발표노트: 핵심 한 문장 — "프롬프트 엔지니어링은 '무슨 말을 거는가', 하네스 엔지니어링은 '모델을 어떤 구조에 넣어 일을 시키는가'." 용어가 진짜 쓰이는 말임을 한 번 짚되(플러그인 예) 홍보처럼 들리지 않게: 우리는 자동생성이 아니라 직접 설계·운영했다. 예상질문: "그냥 멀티에이전트 아니냐?" → 멀티에이전트는 하네스의 한 구성요소일 뿐, 게이트·메모리·스킬까지가 하네스. -->

## 왜 "혼자 쓰기"는 실패하나

1. **정확성** — 숫자를 기억에서 적다가 틀린다(같은 지표라도 n에 따라 값이 다른데 혼동).
2. **일관성** — 그림 번호·캡션·본문 참조가 어긋난다(본문은 Figure 5인데 파일은 옛 이름).
3. **그림** — 기본 matplotlib 출력은 "PPT 슬라이드"처럼 보인다(밀도·정합·잘림).
4. **리뷰** — 자기 글의 약점(과대주장·사족·누락)이 안 보인다.
5. **범위 혼동** — 검토 때 "사전 QA(인용·숫자·그림 점검)"와 "본질적 과학 판단"을 섞어버린다.

→ 각각을 **전담 도구**에 맡기면 사람은 *의사결정*에 집중한다.

## 세 단어로: Agent / Skill / Memory

| | **Agent** | **Skill** | **Memory** |
|---|---|---|---|
| 정체 | 독립 작업자(별도 컨텍스트) | 절차·체크리스트(글로 박은 규율) | 세션 넘어 지속되는 사실/규칙 |
| 언제 | 큰 하위작업 위임·병렬·적대 검증 | "이 일은 이렇게" 표준 절차 | 사용자 선호·프로젝트 상태·교훈 |
| 핵심 | **분업 + 독립 시각** | **재사용 가능한 규율** | **반복 실수 방지** |

> **Agent = 누가 한다 · Skill = 어떻게 한다 · Memory = 지난번에 뭘 배웠나.**

## 도구는 두 곳에 산다

```
~/.claude/  (전역 — 모든 프로젝트 재사용)
   ├─ agents/   research-methodologist, literature-scout,
   │            novelty-strategist, paper-critic, reviewer, design
   └─ skills/   scientific-writing, journal-fit, manuscript-figures,
                statistical-analysis, citation-management, benchmark-sota ...

.claude/  (이 repo 전용 — 프로젝트 지식 내장)
   └─ agents/   manuscript-writer, variant-analysis, variant-adjudicator,
                frontend-dev / backend-dev, paper-orchestrator, presenter
```

> 전역 = 일반 과학 글쓰기 규율 · 프로젝트 = 이 데이터/스택의 비타협 규칙.

| Agent | 역할 | 언제 |

## Memory — 세션을 넘는 학습

이 프로젝트에 **실제 적립된 규칙**(예):

- **완료 과대주장 금지** — 하위작업·서버 단계 남았는데 "done" 금지; 완료/진행/대기/블록 구분.
- **여러 요청 = 각각 보고** — 항목별 상태로.
- **반-조작 교훈** — 변이 수치는 기억이 아니라 JSON/Crossref/ClinVar에서 검증.
- **내부 PM 문서 ≠ 보조자료** — HANDOFF/TODO/STUDY_SUMMARY를 외부 리뷰·원고의 supporting material로 인용 금지.
- **reviewer calibration(혼합)** — 출력 형식 = 생의학 referee 산문 + 점수표(실제 오픈 피어리뷰 벤치마킹).

> 다음 세션이 같은 실수를 **다시 하지 않게** 한다 — 장기 협업자의 기억.

<!-- 발표노트: 이 규칙들이 추상론이 아니라 이 프로젝트에서 진짜 사고가 나서 적립된 것임을 강조. 특히 '반-조작'과 '완료 과대주장 금지'는 이 발표를 만들 때도 적용되는 규율. 한 문장 — "메모리가 없으면 매 세션이 신입사원이다." -->

## 핵심 사상 ① — 자기개선 루프

```
   생성 ──▶ 적대적 critic ──▶ 수정 ──▶ 교훈을 skill/agent/memory에 등록
    ▲                                              │
    └──────────────  다음엔 안 틀림  ◀─────────────┘
```

실제로 일어난 일:

- 그림에 글자 겹침/잘림 발견 → **paper-critic 그림 QA**로 수정
- 그 결함 패턴(박스 텍스트 넘침·축 밖 클리핑·패널 불균형)을 **manuscript-figures 스킬에 등록**
- → 다음 논문에선 처음부터 그 점검을 한다.

> **도구가 매 실수마다 똑똑해진다.**

## 핵심 사상 ② — 내부 critic vs 외부 reviewer (가장 크게 정리된 부분)

| | **paper-critic (내부)** | **reviewer (외부)** |
|---|---|---|
| 목적 | 제출 전 고치기용 적대적 triage | 저널 referee가 실제 제출하는 심사 |
| 자세 | "다 뒤져서 결함 찾기" | "**사전 QA는 됐다 전제**, 본질만" |
| 다룸 | 과장·누락 baseline·통계·leakage·**재현성·그림 시각 QA·수치 vs JSON·인용 점검** | 신규성·방법 타당성·통계·프레이밍 공정성·over-claiming·venue 적합성 |
| **안** 다룸 | — | **인용 정확성·그림 렌더링·수치-출처 대조·참고문헌 충실성**(전부 사전 QA) |
| 산출 | 우선순위 수정 목록 | 권고(accept/revise/reject) + 점수 + 코멘트 |

> "출처/숫자/그림이 맞는지"는 **당연히 끝냈어야 할 사전 작업**이지, *외부 심사자가 리뷰에 적을 내용이 아니다.*

<!-- 발표노트: 오늘 발표의 클라이맥스. 왜 분리가 중요한가 — 스코프를 안 박으면 외부 reviewer가 '내부 critic처럼' 전수 QA로 흘러간다(이 프로젝트에서 실제로 그랬다). 한 문장 — "referee는 인용 오타를 잡는 사람이 아니라 과학을 판단하는 사람이다." -->

## 그 분리를 어떻게 검증했나 — 2단계 운영 + 벤치마킹

**2단계 운영**
1. **내부 패스** = `paper-critic` + `verify_manuscript` 게이트 + `citation-management`/`literature-scout` + 그림 QA → 여기서 *기계적 점검을 전부 끝내고 수정.*
2. **외부 패스** = `reviewer` → 사전 QA 완료를 전제하고 *본질적 판단만.*

**검증 방법 — 실제 오픈 피어리뷰로 벤치마킹**
- **eLife**(Reviewed Preprint), **OpenReview/ICLR**, **F1000Research**의 실제 referee 리포트와 대조.
- 셋 다 "논문 재진술 → 본질 판단 → 권고" 구조이고 **사전 QA를 하지 않음**을 확인.
- → `reviewer` 출력 형식을 **생의학 referee 산문 + 점수표 혼합**으로 고정.

> 교훈: 도구의 **역할 경계**를 정의에 명시해야 한다. 안 그러면 외부 reviewer가 QA로 새어 들어간다.

## 실제로 이렇게 운영했다 (타임라인)

1. **실험·평가** — `variant-analysis`: 파이프라인 + 평가 수트(faithfulness, ablation, Horak 외부 벤치마크, leakage 통제, bootstrap·McNemar) → 결과 JSON.
2. **초안 + 그림** — `manuscript-writer`: STUDY_SUMMARY/JSON에서 프리프린트(EN) + 그림 세트(숫자는 JSON, 그림은 데이터).
3. **선행연구·인용** — `literature-scout`: 참고문헌 검증·교정(검증 불가했던 인용을 실제 문헌으로 정정).
4. **내부 적대 검토** — `paper-critic` **2회**(프로즈 + 그림 레이아웃 QA) → 과대주장·사족·그림 결함 수정.
5. **잠정 판정** — `variant-adjudicator`: beyond-rules/discordant 사례 잠정 판정(사람 확인 전제).
6. **결정론 게이트** — `verify_manuscript`로 헤드라인 수치·DOI 재계산·대조(16/16 통과).
7. **외부 리뷰(2단계)** — `reviewer` 1차 → **Major revision** → R1–R6 반영 → calibrated `reviewer` 2차 → **Minor revision**.
8. **메모리 적립** — 각 단계 교훈을 memory/skill/agent에 등록 → 다음 세션이 반복 안 함.

<!-- 발표노트: 추상틀이 아니라 진짜 돌린 순서. 가장 인상적인 한 줄 — 7번의 "Major → (수정) → Minor"는 시스템이 실제로 개선을 만들어냈다는 증거. 16/16 게이트 통과도 강조. variant-adjudicator는 또 '사람 확인 전제'를 말할 것. 한 문장 — "한 바퀴 = 생성→검증→리뷰→학습, 매 바퀴마다 도구가 똑똑해진다." -->

## 새 역할 두 가지 — presenter & paper-orchestrator

**presenter** — 원고 → 청중별 슬라이드 + 발표노트.
> *이 덱이 그 산출물이다.* (study-group / 한국어 / 20–25분으로 튜닝)

**paper-orchestrator** — 멀티에이전트 워크플로의 **계획자**(실행자가 아님).

```
규칙: 서브에이전트는 다른 서브에이전트를 못 띄운다 (중첩 불가)
  ↓
그래서 orchestrator는 단계 DAG·게이트·Workflow 스크립트를 "계획"으로 낸다
  ↓
실제 실행은  메인 세션  또는  Workflow 도구  가 그 계획대로 에이전트를 띄움
```

<!-- 발표노트: presenter를 회수하는 지점 — "지금 보고 계신 이 덱이 그 에이전트의 산출물입니다." 청중이 좋아함. orchestrator의 핵심 제약(중첩 불가)을 또렷이: 그래서 '계획'과 '실행'을 분리했다 = 하네스 엔지니어링적 사고(도구의 한계를 구조로 우회). 한 문장 — "오케스트레이터는 지휘하지 않는다, 악보를 쓴다." -->

## 실행기 — dynamic workflow (악보를 연주하고, 들여다본다)

`paper-orchestrator`가 쓴 **악보를 연주하는 오케스트라** = Claude Code의 **dynamic workflow**(공식 기능, 서드파티 아님).

- **대규모 fan-out** — 에이전트를 병렬로 띄워 결정론적으로 실행(파이프라인 · producer–reviewer 등).
- **라이브 관측(`/workflows`)** — 각 에이전트가 *지금 뭘 하는지*(phase · tool call · 토큰 · 경과)가 보인다. **P 일시정지 · X 스킵 · 재시도.**

```
orchestrator(계획)  ─▶  dynamic workflow(실행)  ─▶  /workflows(관측·개입)
```

> 멀티에이전트의 "블랙박스" 불안을 정면 해소 — **보이니까 멈추고 고친다.**
> 단, **토큰을 많이 쓴다** → 진짜 병렬·다단계일 때만, 명시적 opt-in.

<!-- 발표노트: 앞 슬라이드의 '계획 vs 실행'을 완성하는 슬라이드 — orchestrator는 악보, dynamic workflow는 연주. 핵심 셀링 포인트는 '관측성': 에이전트가 수십 개여도 각자가 뭘 하는지 보이고 P/X로 개입 가능 → 신뢰가 생긴다. revfactory(서드파티)와 달리 first-party라 신뢰 이슈 없음을 한 번 짚기. 비용 경고 필수: 작은 일엔 메인 세션이 직접. 예상질문 "수백 개도 띄우냐?" → 동시 실행 캡이 있고 opt-in. -->

## 운영 원칙 (체크리스트)

- **검증 게이트** — 모든 헤드라인 수치는 결정론 스크립트로 재계산·대조. 사람·LLM 기억을 믿지 않는다.
- **반-조작** — 인용·숫자는 1차 출처/JSON에서 확인. "같은 모델로 다시 검토"는 자기 환각을 못 잡는다 → 결정론 게이트 + 다른 엔진 + 사람.
- **항목별 보고** — 여러 요청은 각각 상태(완료/진행/대기/블록)로.
- **과신 금지** — critic·reviewer도 틀린다. 적대적 다수결·재현으로 교차검증.
- **비용 감각** — 큰 위임만 에이전트(병렬·반복은 토큰을 쓴다), 작은 건 직접.
- **사람이 최종 판단** — 도구는 초안·검증·일관성. 과학적/임상적 책임은 사람.

<!-- 발표노트: "같은 모델로 다시 검토는 자기 환각을 못 잡는다"가 가장 실무적으로 유용한 한 줄 — 다른 엔진 + 결정론 게이트 + 사람의 3중. 한 문장 — "환각은 더 똑똑한 모델이 아니라 더 독립적인 검증으로 잡는다." -->

## 연구·교육용 — 임상용 아님 (필수 고지)

- 이 프로젝트(체세포 변이 해석 파이프라인)는 **연구·교육·데모용**이다. **임상 진료용이 아니다.**
- `variant-adjudicator`의 변이 판정은 **잠정**이며, **board-certified molecular pathologist의 서명 검토 전제**다.
- 도구는 *초안·검증·일관성*을 돕는다. **과학적/임상적 책임의 최종 주체는 사람.**
- 합성/공개(TCGA 등) 데이터만 사용. 독점 데이터·로직은 비공개.

> 발표의 어떤 수치·판정도 임상 결정의 근거가 아니다.

## 한 장 요약

> **논문 쓰기 = 하네스 엔지니어링.**
> 강한 모델 하나에 다 시키지 말고 —
> (1) 역할 가진 **에이전트로 분업**
> (2) 표준 절차는 **스킬로**
> (3) **내부 검토(QA)와 외부 리뷰(본질)를 분리**
> (4) **적대적으로 검증** (다른 엔진 + 결정론 게이트 + 사람)
> (5) 배운 걸 **도구에 되먹이고** (자기개선)
> (6) 사람은 **판단에 집중.**

*기억할 한 문장: "프롬프트가 아니라 **구조**를 설계하면, 시스템이 매 바퀴마다 똑똑해진다."*
