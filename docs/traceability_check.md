# 원고 수치 추적성 검사 (traceability check)

> 원고에 적힌 모든 수치가 커밋된 결과 파일에서 재현되는지 전수 대조한다.
> 스크립트: `scripts/verify_manuscript_numbers.py` · 출력: `docs/manuscript/number_reconciliation.json`
> 최초 작성 2026-08-05.

---

## 왜 만들었나

2회차 peer review가 재현성 항목에 5점 만점을 주면서 근거를 이렇게 적었다.

> Offline-from-snapshots, 90 tests, scripts named per result;
> **spot-checked** headline numbers reconcile with committed JSONs.

**표본 확인**이다. 이 원고의 핵심 주장은 근거 없이 단정하지 않는 것(`must abstain rather than fabricate`)인데, 정작 원고 자신의 수치는 표본으로만 확인받았다. 그래서 전수로 바꿨다.

---

## 무엇을 하는가

```
원고에서 숫자를 전부 뽑는다        (소수 / 퍼센트 / n = )
        ↓
커밋된 결과 파일에서도 전부 뽑는다
        ↓
원고의 숫자를 결과 파일 풀에서 찾는다
        ↓
못 찾은 것만 등장 문장과 함께 보고한다
```

판정은 두 갈래다.

| 판정 | 뜻 |
|---|---|
| traceable | 커밋된 결과에서 같은 값을 찾음 |
| orphan | **틀렸다는 뜻이 아니라, 맞는지 확인할 경로가 없다는 뜻** |

이 구분을 흐리면 "원고에 오류가 N%"라는 잘못된 문장이 나온다. **검사기가 내놓는 판정의 의미는 만든 사람이 정의해야 한다.**

---

## 설계 결정 네 가지

각각을 안 했을 때 결과가 어떻게 왜곡되는지 함께 적는다.

### 1. 반올림 표기를 인정한다

원본 `0.8432`와 원고 `0.843`은 같은 값이다. 결과 파일에서 값을 읽을 때 소수 2자리, 3자리, 그리고 100배 퍼센트 표기를 미리 만들어 풀에 넣는다.

**안 하면**: 표기 방식 차이만으로 없는 오류가 대량 발생한다.

### 2. 관례값은 대조에서 뺀다

```python
TRIVIAL = {"0.05", "0.01", "0.50", "0.95", "1.00", "0.00"}
```

유의수준 `0.05`는 결과 파일에 없는 것이 정상이다.

**안 하면**: orphan이 부풀려져 실제 문제가 묻힌다.

### 3. 참고문헌과 코드블록은 원고에서 뺀다

```python
body = re.split(r"\n#+\s*References", text)[0]
body = re.sub(r"```.*?```", "", body, flags=re.S)
```

참고문헌의 연도·권호, 코드블록의 상수는 검증 대상이 아니다.

**안 하면**: 검증 대상이 아닌 숫자가 orphan을 채운다.

### 4. 검사기 자신의 출력은 제외한다

```python
SELF_OUTPUT = {"number_reconciliation.json"}
```

**이것이 실제로 사고가 났던 자리다.** 아래 이력 참조.

## 측정 이력

| 시점 | 원고 수치 | traceable | orphan | 비고 |
|---|---|---|---|---|
| 2026-08-05 최초 | 120 | 93 (78%) | **27 (22%)** | 기준선 |
| Table S2 추가 직후 | 157 | 105 (67%) | **52 (33%)** | 파생값이 원자료에 없어 급증 |
| 파생 결과를 탐색 경로에 추가 | 157 | 157 (100%) | **0** | **순환 오류. 무효** |
| 자기 출력 제외 후 | 157 | 132 (84%) | **25 (16%)** | 현재 값 |

### 100%가 나왔던 이유

Supplementary Table S2를 추가하면서 per-class precision/recall/F1이 들어갔다. 이 값들은 원자료를 가공해 얻은 파생값이라 `data/benchmark/`의 JSON에 그 형태로 존재하지 않는다. 그래서 orphan이 27에서 52로 늘었다.

이를 해결하려고 계산 결과가 들어 있는 `docs/manuscript/`를 탐색 경로에 넣었다. 그러자 **100%가 나왔다.**

원인은 그 폴더에 검사기 자신의 출력 `number_reconciliation.json`이 있었기 때문이다. 그 파일에는 원고에서 뽑은 모든 수치가 traceable·orphan 목록으로 들어 있으므로, 검사기가 자기가 뽑은 숫자를 자기 출력에서 다시 찾아 **무조건 전부 통과**시켰다.

`SELF_OUTPUT`으로 제외하고 다시 돌려 16%를 얻었다.

### 여기서 확인된 것

- **검사기가 자기 산출물을 근거 풀에 넣으면 항상 통과한다.** 판정이 100%로 나오면 통과를 축하하기 전에 왜 100%인지 먼저 본다.
- **계산 스크립트를 만들면 추적률이 실제로 오른다.** 수치가 120개에서 157개로 37개 늘었는데 orphan은 27에서 25로 줄었다. `scripts/eval_precision_recall.py`가 파생값의 근거가 됐기 때문이다.

---

## 현재 남은 25개

| 갈래 | 성격 | 처리 방향 |
|---|---|---|
| 성능 지표 (파생값) | 원자료에서 계산되나 계산 위치가 문서화 안 됨 | 계산 스크립트를 만들어 결과를 커밋 |
| 본문 계산 퍼센트 (`21.4` 등) | 분모가 본문에 없음 | `21.4% (12/56)` 형태로 분모 병기 |
| 인용 수치 (`75.5` 등) | 타 논문에서 인용한 값 | 인용 표기로 충분. 별도 목록으로 분리 예정 |

세 번째 갈래는 성격이 달라 같은 잣대로 재면 안 된다. 다음 개선에서 `orphan`을 `derived` / `underspecified` / `cited`로 나눌 계획이다.

## 실행

```bash
python scripts/verify_manuscript_numbers.py       # 수치 추적성
python scripts/eval_precision_recall.py           # per-class 지표 (Table S2 근거)
```

둘 다 표준 라이브러리만 쓰고 네트워크를 타지 않는다. 같은 입력이면 같은 결과가 나온다.

원고를 고칠 때마다 첫 명령을 돌려 orphan이 줄어드는지 확인한다.
